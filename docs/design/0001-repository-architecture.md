# 0001 仓库架构：静态画廊，按演示隔离

- 状态：已采纳
- 日期：2026-10-22

## 背景

这个项目会容纳多个历史题材的动画演示：春秋战国的疆域兼并、罗马行省的扩张、日本战国的势力消长，可能还有人口迁徙、贸易网络这类形态完全不同的题材。需要一个能长期扩展、且不需要频繁重构的仓库结构。

同时定下两条约束：页面十年后仍能打开；外部贡献者能在不读完全部代码的情况下改一处数据。

## 考虑的方案

### 方案 A：静态画廊，每个演示独立

每个演示是 `demos/<id>/` 下的自包含目录，含自己的 `index.html`、数据、渲染脚本与样式。根目录一个索引页。零构建。

优点是新增演示等于新增目录，互不干扰；单个演示可以自由选择技术路线，甚至完全重写渲染层。缺点是公共逻辑会重复，若干演示之后维护成本上升。

### 方案 B：共享引擎 + 数据驱动

抽一个 `shared/` 引擎，封装投影、时间轴、图例、事件卡片的通用逻辑，每个演示只提供数据与少量配置。

优点是第二个演示起成本显著下降，行为一致。缺点是必须现在就知道哪些是共性。从一个演示里提炼的「通用引擎」，多半是把偶然当必然，后面要么被架空，要么被反复改写。

### 方案 C：Astro 或 Vite 站点

有模板、组件、路由，SEO 与内容组织更规范。

优点是工程化程度高，适合内容量大的站点。缺点是引入 Node 构建链与依赖版本维护，与「十年后仍能打开」的约束直接冲突。依赖过期后，仓库就变成需要考古才能构建的状态。

## 决定

采用方案 A，但按方案 B 的形状组织目录。

具体做法：

- 每个演示的目录放在 `demos/<id>/`，`id` 与数据里的 `META.id` 一致，校验脚本强制这一点
- 演示内部强制数据与渲染分离：`data.js` 只放数据，`app.js` 只放画法与交互
- 每个演示自带 `style.css`，不强制视觉统一
- 站点级共享样式只有 `assets/site.css`，只服务画廊首页与文档页
- 不设 `shared/` 目录，等第二个演示写完再决定往里放什么

## 后果

好的方面：

- 新增演示零协调成本，不需要改任何配置
- 单个演示可以独立演进，甚至换掉整个渲染层，不影响其他演示
- 零构建，克隆即可打开，没有工具链腐化问题

需要接受的代价：

- 公共逻辑在演示之间是复制的，改一处共性问题要在多处同步
- 没有类型系统与单元测试框架，靠 `scripts/check.mjs` 兜住数据层的错误
- 画廊首页是手写的卡片，新增演示要手动登记（校验脚本会检查是否漏登记）

## 后续

第二个演示完成后，回头评估这三件事是否真的重复：投影与坐标换算、时间轴控件、事件与归属的状态推导。只把确认重复的部分提取到 `shared/`，并且保持「删掉 shared 也不影响任何单个演示独立打开」这一性质。

如果提取后发现必须让所有演示共享同一套 DOM 结构才能工作，说明提取过度，应当退回到方案 A。
