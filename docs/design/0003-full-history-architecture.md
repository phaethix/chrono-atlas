# 0003 从两个演示到一部通史：信息层级与多卷归集

- 状态：提议，待确认
- 日期：2026-10-25

## 背景

现在仓库里有两个演示：一个画春秋战国的疆域兼并，一个画史前的文化区。各自都成立，合起来却不成体系：

- **人能看地，看不到人。** 疆域图里有「秦」，没有秦孝公；文化区图里有「仰韶」，没有女娲。
- **看一卷，接不上下一卷。** 两卷之间共同提到的黄帝、禹、周人，在各卷里是互不相干的字符串。
- **加一卷，就得手写一张卡片、一份数据、一套校验规则。** 第三卷开始，维护成本会压过内容本身。

要装下 24 卷，缺的不是渲染，是三样东西：**跨卷稳定的实体标识、关系层、逐卷录入的流程**。这份文档给的是这三样。

## 一、信息层级

五层，从纵向的叙事容器到横向的索引：

| 层  | 单位         | 量级（估）  | 存放                  | 例子                                        |
| --- | ------------ | ----------- | --------------------- | ------------------------------------------- |
| L0  | 卷           | 24          | `catalog/manifest.js` | 第五卷《从春秋到战国》                      |
| L1  | 章           | 122（已知） | `catalog/manifest.js` | 第一章 夏娃造反                             |
| L2  | 实体         | 1500—2500   | `corpus/`             | `person-huangdi`、`polity-qin`、`place-yin` |
| L3  | 关系         | 3000—6000   | `corpus/relations/`   | 黄帝 → 昌意（父子）、尧 → 舜（继位）        |
| L4  | 陈述（事件） | 1500—2500   | `demos/<id>/data.js`  | 前 2600 年，涿鹿之战                        |

三句话概括这个层级：

- **卷是纵的**：一册书一个叙事单元，有起止、有章目、有立场。
- **实体与关系是横的**：一个人可以出现在多卷里，但只建一条记录。
- **视图是斜的**：同一批数据，地图看空间，谱系看血缘，年表看先后，网络看师承。

地图只是视图之一。第一卷之所以像地图，是因为它的材料恰好能落到区域上；《百家争鸣》多半要靠人物与师承网络，《大航海时代》要靠路线。**不要把 24 卷都做成 24 张地图。**

## 二、模块划分

```
chrono-atlas/
├── catalog/
│   └── manifest.js        24 卷：卷次、书名、分期、状态、章目、已有视图
├── corpus/                跨卷共享，横向索引
│   ├── core.js            命名空间与注册函数
│   ├── schema.js          词表：实体类型、关系类型、证据等级（唯一权威）
│   ├── people/<era>.js    人物分片，按时代切，不按卷切
│   ├── relations/<era>.js 关系边，与人物分片同代
│   ├── polities/          群体：王朝、诸侯、部族、学派（待建）
│   ├── places/            地名录：都城、战场、遗址，带经纬度（待建）
│   └── texts/             文献：经史、出土文字（待建）
├── demos/<id>/            卷的视图：页面、本卷事件、地图、样式
├── views/                 被两卷以上用到的画法才抽到这里（待建）
├── scripts/               check.mjs、serve.mjs
└── docs/                  规范与决策记录
```

标「待建」的目录在 P1—P2 落地。现在只有 `people/` 与 `relations/` 两片，够跑通关系模型，不够覆盖 24 卷。

三条边界，破了任何一条，这套结构就会退化成一个大杂烩。

**一、数据与渲染。** 沿用 0001：`data.js` 不碰 DOM，`app.js` 不写坐标与史实。语料层同理：`corpus/` 里没有一句叙事，只有人与关系。

**二、横向与纵向。** `corpus/` 不写「这一卷讲了什么」，卷不复制人物的生卒与别名。卷要引用人物，只写 ID。

**三、稳定与临时。** 实体 ID 一旦发布就不再改，改名只加 `alias`。派生数据（反推的子女、兄弟）不落盘，由视图现算。

### 为什么人物按时代分片，不按卷分片

孔子同时出现在《青春志》《从春秋到战国》《百家争鸣》三卷里。按卷存，他会变成三条记录；按时代存，他只有一条，三卷各自引用。分片只是文件大小的妥协，不是归属关系。

## 三、数据模型

### 标识

规则：`<kind>-<slug>`，全库唯一，小写拉丁字母、数字、连字符。

```js
'person-huangdi'   'polity-qin'   'place-yin'   'text-shiji'
```

带前缀的理由不是好看，是防撞：`zhou` 既可能是周国、周地、周人，也可能是一个现代地名。前缀把类型写进标识，引用时不用回头查表。

不用中文 ID：拼音 slug 可以被任何编辑器、URL、CSS 选择器安全处理，中文 ID 在复制粘贴与编码转换里经常出事。中文只出现在 `n` 与 `alias` 里。

**ID 永不复用。** 删掉的实体，它的 ID 也不给后来者。否则三年前的链接会指向另一个人。

### 实体

四类，字段见 `corpus/schema.js`：

| 类型     | 必填 | 主要字段                                | 说明                          |
| -------- | ---- | --------------------------------------- | ----------------------------- |
| `person` | `n`  | `alias` `from` `to` `role` `note` `src` | 生卒无考就写 `null`，不要编年 |
| `polity` | `n`  | `alias` `from` `to` `kind` `note` `src` | 王朝、诸侯、部族、学派都算    |
| `place`  | `n`  | `alias` `lon` `lat` `modern` `note`     | 与地图区域是两回事，见下      |
| `text`   | `n`  | `alias` `from` `to` `note` `src`        | 经史、诸子、出土文献          |

**地点与区域不是一回事。** 区域（`REGIONS`）是一卷自己的多边形切分，换一卷就得重切；地点（`place`）是全库共用的一个点或一个遗址，长安在十卷里都是同一个 `place-changan`。地图上的区域可以声明 `place: 'place-changan'`，但不要把两者合并。

### 关系

方向约定：**从「上位 / 主动」指向「下位 / 被动」**。亲 → 子，师 → 生，前任 → 继任，加害者 → 受害者。

词表（`corpus/schema.js` 是唯一权威）：

| kind         | 方向 | 细分 role                                      | 用途                     |
| ------------ | ---- | ---------------------------------------------- | ------------------------ |
| `parent`     | 有向 | `father` `mother` `adoptive`                   | 亲子，只存亲 → 子        |
| `spouse`     | 无向 | `primary` `secondary` `later`                  | 婚姻，正妻与妾要分开     |
| `sibling`    | 无向 | `same-mother` `different-mother` `same-father` | 只在史料明记时写         |
| `succession` | 有向 | `throne` `title` `school`                      | 继位，兄终弟及与禅让同边 |
| `teacher`    | 有向 | —                                              | 师承                     |
| `ruler`      | 有向 | —                                              | 君臣                     |
| `ally`       | 无向 | —                                              | 同盟                     |
| `rival`      | 无向 | —                                              | 敌对                     |
| `killed`     | 有向 | —                                              | 加害 → 受害              |
| `author`     | 有向 | —                                              | 人 → 文献                |
| `founder`    | 有向 | —                                              | 人 → 群体 / 学派         |

只有 `parent` 是必录的，其余按史料补充。**子女与兄弟由视图反推**：录一份亲 → 子，就能同时得到子 → 亲、兄弟、世代。落盘两份必然不同步，这是这类数据最常见的腐烂方式。

对称关系（婚姻、兄弟、同盟、敌对）只存一条，视图两侧都画。校验脚本会把 `a→b` 与 `b→a` 同时存在判为重复。

### 陈述（事件）

沿用 `EVENTS`，增加一个可选字段：

```js
{ y: -2600, t: 'legend', src: 'legend', s: '黄帝与蚩尤战于涿鹿。',
  refs: { people: ['person-huangdi', 'person-chiyou'], place: ['place-zhuolu'] } }
```

`refs` 让事件与实体打通：点开「涿鹿」，能看到参战的两个人；点开黄帝，能看到他参与的所有事件。这一层做不做，决定图谱能不能从「图」变成「书」。

### 证据

两个字段，不要混：

- `src`：证据的性质，`arch` / `legend` / `text`，进图例、进侧栏标签。
- `source`：具体出处，如 `《史记·五帝本纪》`，进卡片与附录。

关系也要标。第一卷第 22 页那种「炎黄同出少典」的说法，边上必须能看见「传说」两个字，否则整套东西就退化成民间故事集。

## 四、关系怎么变成图

谱系视图不是力导向图。族谱要有代际秩序，用力导向会得到一张好看的毛线团。

布局规则：

1. **代 = 从根出发的最长路径。** 无父无母者为根，子女代数为父代 +1；一夫多妻时取最大，宁可把某人放低一代，也不要让子代高过父代。
2. **同代排序**：出生年 → 所属房支 → 显式 `order`。没有生年就按父辈顺序排，保持兄弟相邻。
3. **边**：亲子实线自上而下，婚姻横线连接夫妻，继位虚线箭头，敌对红色虚线。
4. **交互**：悬停高亮全部祖先与后代；点击聚焦并显示生平卡片；时间滑杆只显示该年已出生且未卒的人。

这套规则用 SVG 直接画，不需要布局库。第三卷之前不抽 `views/kin`，等第二处用到再说——与 0002 的判断一致。

## 五、多卷归集流程

一册书从「未录入」到「已成视图」，固定七步：

1. **登记卷目**：`catalog/manifest.js` 里把 `status` 改成 `partial`，补 `id` 与 `views`。
2. **录实体**：人物先查有没有——有就加 `alias`，没有才新建。一个实体只建一次。
3. **录关系**：只写亲 → 子与确有出处的边。没把握的写进 `note`，不要建成边。
4. **录事件**：本卷 `data.js` 的 `EVENTS`，用 `refs` 指向实体。
5. **录地图**：本卷的区域多边形与归属变更（如果这卷需要地图）。
6. **写 README**：史料依据、异说取舍、已知简化。这是评审的依据，不是装饰。
7. **跑校验**：`node scripts/check.mjs`，通过后 `status` 改 `done`。

状态机只有三档：`planned` 未开始 → `partial` 有数据无完整视图 → `done` 有成型的视图。**不允许 `done` 却没有视图**，也不允许跳过 `partial` 直接标 `done`。

### 一册新卷的检查清单

- 卷次没有被跳过，书名与纸质版一致
- 新实体没有与已有 ID 重名，别名补进了旧记录
- 关系两端都存在，`kind` 与 `role` 在词表内
- 亲子关系无环（脚本会拦）
- 事件年份落在本卷视图的区间内
- 传说类事件标了 `src:'legend'`
- 本卷用到的分片都写进了页面的 `<script>` 列表

## 六、校验

`scripts/check.mjs` 从 23 项扩到 25 项，新增两类：

| 检查                                           | 拦住的错误                                |
| ---------------------------------------------- | ----------------------------------------- |
| 实体 ID 形如 `kind-slug`，全库唯一             | `person-黃帝` 这类编码混入、周与周地撞 ID |
| 关系两端存在、`kind` 与 `role` 在词表内        | 拼错 `succession`、把父子写成 `child`     |
| 亲子关系无环                                   | 父子录反、抄录时把祖先挂到了后代名下      |
| 对称关系不重复存                               | 婚姻录两遍，视图画出两条线                |
| 卷目 24 卷、卷次连续、状态合法                 | 加卷时漏号、跳号                          |
| `views` 指向真实目录，且每个演示都登记到某一卷 | 新建演示忘了进卷目，或卷目写了错路径      |

负向测试过：故意指向不存在的人物、故意造一个亲子环，脚本都能报出具体位置。

## 七、迁移

- **第一卷《祖先》**：`demos/zuxian/` 直接就是第一卷，`status: done`。五帝谱系 22 人、31 条边已进语料，作为关系模型的第一个样本。
- **春秋战国演示**：跨第四、五、六卷，登记在第五卷，`status: partial`。它的疆域数据不迁，等这 24 卷的人物录进来再补 `refs`。

## 九、代价

- **语料库会成为最大的维护负担。** 24 卷大约两千个人物、数千条边，任何一个错都会顺着图扩散。这是这套结构的固有成本，只能靠校验和出处压住。
- **ID 不能改。** 一旦发布，错别字也得靠别名兜。所以起 ID 时要慢。
- **24 卷不是 24 个演示。** 有的卷没有地图，有的卷只有十几个人物。不要为了整齐给每卷都配一张图。
- **图谱会诱导过度连接。** 「某某是某某的后代」这类说法在史书里遍地都是，多半是追述。边可以画，`src` 必须诚实。

## 十、不做什么

- 不做数据库、后端、账号。仍然是静态文件，仍然双击可开。
- 不做从原文自动抽取人物与关系。抽取的错会以最难看的方式进入图谱。
- 不追求收录所有人。只收与叙事有关、且在史书里出现过两次以上的。
- 不把 24 卷做成一条统一时间轴。卷与卷重叠（魏晋与南北朝、北宋与南宋），强行拉直会丢信息。
